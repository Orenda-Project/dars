# Decision Log — NCP English G1 Seed

Decisions are **frozen** once recorded. To revise: ask the user, mark the old as "Superseded by D-N+1 on YYYY-MM-DD", and add the new entry. Never overwrite. Both stay.

**D-1: Scope is exactly one cell: NCP × English × Grade 1.** *Rationale:* mirrors the existing Dars × English × G1 seed so the breakdown engine and downstream services are exercised against a real-data path identical in shape to the synthetic one. Other grades/subjects can be added later, one cell at a time. *Apply:* extraction pipeline filters strictly to `grade.short_code = 'G1'` and `subject.short_code = 'Eng'`. *Decided:* 2026-05-20.

**D-2: ~~NCP SLO `domain` → `lp_type` mapping is hand-authored in the seed module, not derived at runtime.~~** **Superseded by D-11 on 2026-05-20.** *Original rationale:* NCPSLO has no native `recommended_lp_type` field, only a `domain` and `language_skills` array; static mapping table seemed appropriate. *Superseded because:* lp_type is more accurately a property of the sub-SLO (granular outcome), not the SLO (broad outcome). One SLO can break into sub-SLOs warranting different lp_types. Domain-based mapping at SLO level loses that fidelity.

**D-3: ~~Data is extracted once offline, frozen as JSON, committed to the dars repo.~~** **Superseded by D-18 on 2026-05-20.** *Original rationale:* keep Railway boot deterministic, runtime decoupled from external deps. *Superseded because:* an existing pre-v2 script (`scripts/import_books.py`) already established the "ETL directly into Dars" pattern, and the user's preference is to import once into Dars staging directly without intermediate JSON. Since data is added once (not on every boot), runtime-decoupling is moot. JSON freeze adds review surface for diff but doubles the integration work (extract step + seed step) for no operational benefit when there's no Phase 2 re-application.

**D-4: Existing Dars seed and Aisha demo tenancy are untouched.** *Rationale:* the demo is the basis for every existing test, screenshot, and dashboard. Re-seeding has blast radius. NCP is purely additive — a new curriculum row in lookups, new SLO/sub-SLO/book/topic rows, all keyed to the NCP curriculum FK. *Apply:* never modify `lookups.py:GRADES/SUBJECTS`; never modify `slos_dars_english_g1.py` / `book_dars_english_g1.py`; never modify `tenancy_demo.py`. *Decided:* 2026-05-20.

**D-5: Sub-NCP-SLOs sourced by running Schema's breakdown once, freezing the output.** *Rationale:* sub-SLOs don't exist as static data anywhere — Schema's breakdown service is what generates them via LLM from top-level NCP SLOs. Schema's output cache (`Schema/output/`) is currently empty. Running once and freezing keeps the seed reproducible without making the dars repo runtime-coupled to Schema or an LLM. *Apply:* extraction script invokes Schema (either by import or subprocess; see `03-phase-1`); resulting markdown + parsed JSON are committed under `seeds/ncp_english_g1/`. Re-running requires explicit user approval to overwrite. *Decided:* 2026-05-20.

**D-6: Topic ↔ sub-SLO mappings come from Schema's `map_topics_to_ncp_slos`, also frozen.** *Rationale:* same logic as `D-5`. Schema is the canonical place where topics get mapped to sub-NCP-SLOs (via LLM, using the breakdown markdown as reference). Freezing the output here keeps dars decoupled from Schema at runtime. *Apply:* one combined extraction script run produces both sub-SLOs and mappings; both committed. *Decided:* 2026-05-20.

**D-7: Topics come from Schema's topic-extraction output, not from `book_library.BookChapter.chapter_text` JSON.** *Rationale:* `book_library` has no Topic model — `chapter_text` is unstructured JSON prose. Schema already extracts discrete "topics" from book content as part of its pipeline; reusing that extraction keeps topic granularity consistent with how Schema/LP Assistant think about them. If Schema's extraction is unavailable for a chapter, that chapter is seeded with one synthetic topic per chapter as a fallback (clearly flagged). *Apply:* extraction script reads Schema topic outputs first; falls back to "one topic = one chapter" with explicit `is_synthetic_fallback: true` marker. *Decided:* 2026-05-20.

**D-8: NCP curriculum lookup row uses code `NCP` and label `National Curriculum of Pakistan`.** *Rationale:* keeps consistency with existing lookup naming (short code + descriptive label). Code `NCP` is short, unambiguous, FK-safe. *Apply:* add to `CURRICULUMS` in `seeds/lookups.py`. UUID derived via `seed_uuid("curriculum:NCP")` to keep deterministic IDs. *Decided:* 2026-05-20.

**D-9: Extraction script is run by a developer on their workstation, not on Railway. Data source is live `fde_staging` Postgres via direct read-only SQL — not the .dump file.** *Rationale:* the live DB matches what taleemabad-core has now (the dump is a snapshot), and SQL queries are easier to iterate on than loading a 670MB dump. Schema also requires an LLM key, which isn't in the dars Railway env. Keeping extraction local — both DB connection and Schema/Claude calls — keeps Railway boot deterministic and credential-free. *Apply:* extraction script reads two env vars: `FDE_STAGING_DATABASE_URL` (read-only `fde_staging` creds) and `ANTHROPIC_API_KEY`. README documents how a developer obtains read-only creds. *Decided:* 2026-05-20.

**D-10: ~~No new schema migration for this feature.~~** **Superseded by D-12 on 2026-05-20.** *Original rationale:* feature is purely additive data; existing tables sufficient. *Superseded because:* D-11 puts lp_type on sub-SLOs, which is a new column. One small additive migration is the right shape.

---

**D-11: lp_type is assigned per sub-SLO by Claude during the offline extraction; ignore the NCPSLO `domain` field entirely.** *Rationale:* sub-SLOs are the granular learning step that actually maps onto a lesson — different sub-SLOs of the same SLO can warrant different lp_types (e.g. a vocabulary sub-skill vs a writing sub-skill of one comprehension SLO). Claude is well-suited to read the sub-SLO statement and pick from the 5-value enum; the result is frozen into the fixture so runtime is deterministic. *Apply:* in the extraction pipeline, after Schema produces sub-SLOs, a Claude-backed mapper assigns `lp_type ∈ {reading, comprehension_word_meanings, comprehension_qa, grammar, creative_writing}` per sub-SLO. The decision lives in `seeds/ncp_english_g1/sub_slos.json` as the `lp_type` field on each sub-SLO row. NCPSLO `domain` and `language_skills` are not read. *Decided:* 2026-05-20.

**D-12: Add nullable `recommended_lp_type TEXT` column to `sub_slos` table.** *Rationale:* D-11 needs a place to store per-sub-SLO lp_type. Existing schema only has it on `slos`. Nullable + additive: existing Dars sub-SLOs stay NULL (they inherit via parent SLO's existing value), new NCP sub-SLOs populated by the seed. No backfill needed. *Apply:* new migration `server/src/dars/migrations/<ts>_sub_slos_add_recommended_lp_type.sql`. Updates `02-data-model.md` of the v2 rebuild plan in the same PR (rebuild plan's data model is canonical; this feature's plan defers to it). *Decided:* 2026-05-20.

**D-13: lp_type resolution prefers sub-SLO over parent SLO when both are set.** *Rationale:* if D-12's new column is populated, it's the most specific signal and should win over the parent SLO's `recommended_lp_type`. Existing breakdown heuristic (`breakdown/lp_type_heuristics.py`) is updated to check sub-SLO first, then fall back to SLO's value, then the existing subject-default chain. Backward-compatible for Dars (sub-SLO column is NULL → falls back to SLO value → identical behavior). *Apply:* edit `lp_type_heuristics.py` and `auto_build_service.py`'s topic-lp_type query to JOIN sub_slos and pick its `recommended_lp_type` first; document the precedence chain in the heuristic's docstring. *Decided:* 2026-05-20.

**D-14: Claude-mapper uses Anthropic SDK directly with prompt caching; no separate service.** *Rationale:* the mapper is run once offline by a developer; it's not a runtime service. The dars repo already uses Anthropic SDK for `claude-api` workflows. Avoid creating new infrastructure for a one-shot job. *Apply:* mapper lives at `scripts/lp_type_classifier.py`; reads `ANTHROPIC_API_KEY` from the developer's env; uses `claude-haiku-4-5-20251001` (cheapest + sufficient for classification); prompt caches the 5-value enum description + few-shot examples across sub-SLOs to keep cost minimal. *Decided:* 2026-05-20.

**D-15: Book is `fde_staging.book_library_book.id = 1171`. Script accepts `--book-id` for re-runnability.** *Rationale:* the user picked 1171 ("English G1 Taleemabad" by Taleemabad publisher, OnProd, HYPER_SPECIFIC). Seeding all 27 English-G1 books in fde_staging would be wrong — we want a canonical NCP English G1 book. The `--book-id` arg lets the same script run again later for a different book without forking. With D-18 (direct ETL, upsert), re-running is idempotent: same book id re-runs are no-ops; different book id adds another book row. *Apply:* CLI defaults to `--book-id 1171`. *Decided:* 2026-05-20.

**D-16: Use `book_library_bookchapter` rows for chapter boundaries (number/title/page range), but use `book.book_text` for chapter prose. Ignore `chapter.chapter_text`. No `is_active` filter on chapter rows.** *Rationale:* live investigation showed that on book 1171, `chapter.chapter_text` is real for some chapters and a 4-char stub for others, while `book.book_text` consistently contains real prose for all 12 chapters keyed by `pdf_page_no`. The chapter table is the right *index* (chapter ordering, titles, page ranges); `book.book_text` is the right *content*. Slicing `book_text` on `pdf_page_no BETWEEN start_page AND end_page` reconstructs per-chapter prose reliably. Excluding `is_active=f` chapter rows would lose 4/12 chapters whose underlying book content is actually fine. *Apply:* extraction reads chapter rows with no `is_active` filter; reads `book.book_text` once; slices by page range per chapter. `chapter.chapter_text` is never read. *Decided:* 2026-05-20.

**D-17: Reads from fde_staging use `CORE_STAGING_DB_*` env vars (already in `dars/.env`), not new ones.** *Rationale:* those env vars already exist in `dars/.env` and are the standard way the dars repo reaches the taleemabad-core staging DB. Avoid introducing parallel naming. *Apply:* extraction script reads `CORE_STAGING_DB_HOST`, `CORE_STAGING_DB_PORT`, `CORE_STAGING_DB_NAME`, `CORE_STAGING_DB_USER`, `CORE_STAGING_DB_PASSWORD`. Read-side connection always sets `search_path = fde_staging, public` and runs in a `BEGIN READ ONLY; ... ROLLBACK` transaction to make accidental writes impossible. *Decided:* 2026-05-20.

---

**D-18: Single phase, one PR. Script writes directly to Dars staging DB via SQL upserts; no JSON freeze, no runtime seed integration.** *Rationale:* per user preference, simpler integration model. Data is loaded once into Dars staging by a developer; the runtime `v2_seed` is unchanged. Idempotent upserts (`ON CONFLICT DO UPDATE` keyed on natural-unique columns) make re-runs safe. The migration for `sub_slos.recommended_lp_type` (D-12) ships in the same PR; Railway applies the migration on deploy, the developer then runs the script locally pointing at Dars staging. *Apply:* feature collapses to a single Phase 1. Phase 2 doc is removed. Old features F2.1 (migration) and F2.2 (heuristic updates) move into Phase 1. No `seeds/ncp_english_g1/` directory is created. *Decided:* 2026-05-20.

**D-19: Script connects to Dars staging via new env var `DARS_STAGING_DATABASE_URL` in `dars/.env`.** *Rationale:* user will add the Railway-Postgres public TCP URL for the Dars staging DB; same shape as the existing `CORE_STAGING_DB_*` block. One-time .env update; matches how the user already manages staging-DB access for other tooling. *Apply:* script reads `DARS_STAGING_DATABASE_URL`; fails fast with clear message if missing. Connection is read-write, wraps everything in a single transaction (BEGIN → all upserts → COMMIT). On any error the transaction rolls back. *Decided:* 2026-05-20.

Its book-fetch SQL is reused in the new script — git blame from the new file is sufficient attribution. *Apply:* `git rm scripts/import_books.py` as part of the close-out commit. *Decided:* 2026-05-20.
