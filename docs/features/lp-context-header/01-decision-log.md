# Decision Log — LP Context Header

Decisions are frozen. To revise: ask the user, mark the old entry "Superseded by D-N+1 on YYYY-MM-DD", add the new one. Both stay.

---

**D-1: This is a presentation + data-completeness feature, not a schema change.** *Rationale:* every fact we need (chapter via `book_chapter_id`, topic via `topic_id`, `lp_type`) already exists in the DB. The work is (a) making sure each LP-display endpoint *returns* all three, and (b) presenting them clearly and consistently. No new tables, no migrations. *Apply:* `02-data-model.md` describes response-shape deltas only; no `.sql` files. *Decided:* 2026-06-15 (planning).

**D-2: Visual hierarchy = topic primary, chapter eyebrow above, LP type as a badge.** *Rationale:* the user's chosen layout. The topic is the most meaningful "what is this lesson about" anchor, so it's the headline; the chapter situates it (small eyebrow above); the LP type — the thing that was "very subtle" — becomes a distinct colored badge so it reads at a glance. *Apply:* the `LpContextHeader` molecule renders exactly this; every display site uses it (or its compact variant, D-6). *Decided:* 2026-06-15 (user via AskUserQuestion).

**D-3: One `lpTypeLabel()` map turns raw enum values into human-readable labels.** *Rationale:* today raw strings like `comprehension_word_meanings` are shown verbatim — cryptic. A single map in `lib/` is the only place this translation lives, so labels stay consistent across all sites. Mapping: `reading`→"Reading", `comprehension_word_meanings`→"Comprehension: Word Meanings", `comprehension_qa`→"Comprehension: Q&A", `grammar`→"Grammar", `creative_writing`→"Creative Writing", `revision`→"Revision", `concrete`→"Concrete", `pictorial_and_abstract`→"Pictorial & Abstract", `word_problems`→"Word Problems". Unknown values fall back to a title-cased, underscore-split version of the raw value (so a new backend enum never renders blank). *Apply:* badge text and any inline type text go through this; never render `lp_type` raw again. *Decided:* 2026-06-15 (planning).

**D-4: Backend fills context gaps only where a display site needs it.** *Rationale:* of the LP-returning endpoints, `/csts/{id}/lesson-slots` and `/csts/{id}/timeline` already carry chapter + topic + lp_type. The gaps that a user actually sees: (a) `/today` has chapter (`current_chapter`) + lp_type but only `topic_id` — needs `topic_title`; (b) the lesson-slot **detail** endpoint (`GET /class-lesson-slots/{id}`, backing the LP slide-over) has topic_text + lp_type but no chapter — needs `chapter_number` + `chapter_title`; (c) `/me/calendar` has only lp_type + topic_id. We add fields to (a) and (b) because those back prominent display sites. We do **not** expand `/me/calendar` in this feature — its cells are dense and the calendar is out of the user's "wherever we show LP" complaint's hot path; deferred (see D-5). *Apply:* phase 1 touches only the `/today` loader and the slot-detail loader. *Decided:* 2026-06-15 (planning).

**D-5: `/me/calendar` and the dashboard failures-list are out of scope.** *Rationale:* the calendar shows compact day cells (chapter+topic would crowd them) and the failures list is an admin debugging tool, not a teacher-facing LP view — neither is what the user means by "wherever we show LP." Calendar may get the compact header (D-6) in a later pass if asked; failures list stays as-is. *Apply:* phase 2 does not modify `app/dashboard/generations/failures/page.tsx`; calendar cell rendering is left unchanged. *Decided:* 2026-06-15 (planning).

**D-6: The header has a `compact` variant for dense rows.** *Rationale:* the full stacked header (eyebrow + headline + badge) suits cards and slide-overs, but timeline/syllabus rows are dense one-liners. `LpContextHeader` takes a `variant` prop: `default` (stacked) and `compact` (single line — chapter muted · topic · type badge inline). Same data, same label map, same badge styling, different layout. *Apply:* cards/slide-over use `default`; timeline rows use `compact`. *Decided:* 2026-06-15 (planning).

**D-7: The LP slide-over (`LPViewer`) gains the header at its top.** *Rationale:* the full LP view currently shows neither chapter, topic, nor type — it jumps straight to SLO chips + body. That's the most important place to fix: when a teacher opens the actual lesson plan, they should see what it is. The slot-detail endpoint already returns topic_text + lp_type; after D-4(b) it also returns chapter. *Apply:* `LPViewer` renders `LpContextHeader` (default variant) above the Covered SLOs section. *Decided:* 2026-06-15 (planning).

**D-8: Clicking a chapter in the teacher-app syllabus opens a dedicated chapter page, not an inline accordion.** *Rationale:* user request mid-planning. Today the syllabus (the `?tab=syllabus` view of `/teacher-app/classes/[cst_id]`) expands a chapter inline via `expandedChapterId` accordion state. The user wants a focused per-chapter page with its own URL and a back link to the all-chapters list. *Apply:* new route `/teacher-app/classes/[cst_id]/chapters/[position]`; the syllabus chapter row becomes a navigation `Link` to it (the inline accordion expand is removed/retired for the chapter body — see D-11 for what happens to `ChapterContents`). *Decided:* 2026-06-15 (user message).

**D-9: The chapter page is keyed by chapter `position`, not `book_chapter_id`.** *Rationale:* `position` is the stable join key between the syllabus chapter list (`ClassPathChapter.position`) and the timeline items (`TimelineLessonItem.breakdown_chapter_position`); the explorer confirmed both derive from the same ordered class path. A position-keyed URL is also human-readable (`/chapters/3`). *Apply:* route param is `[position]`; the page finds its chapter via `chapters.find(c => c.position === Number(position))` and its slots via `timeline.filter(t => t.breakdown_chapter_position === Number(position))`. *Decided:* 2026-06-15 (planning).

**D-10: The chapter page is a self-fetching client component (works on refresh / direct link).** *Rationale:* user wants it "client side, immediately renders." A self-sufficient route that fetches `getSyllabus(cstId)` + `getTimeline(cstId)` on mount survives refresh, direct links, and back/forward — the app passes no cross-route state today, so relying on parent state would break those. "Immediate" is satisfied by a client component that paints its shell + back link instantly and fills a light skeleton when data lands. *Apply:* `page.tsx` is `"use client"`, reads `cst_id`+`position` from `useParams`, fetches both endpoints in `useEffect`, renders shell→skeleton→content. *Decided:* 2026-06-15 (user via AskUserQuestion).

**D-11: The chapter page reuses the existing chapter-body rendering; the syllabus row stops expanding.** *Rationale:* `ChapterContents` / `TimelineRow` already render a chapter's lesson + assessment slots; the chapter page should reuse them (with the compact LP-context header from D-6) rather than reinvent. The syllabus `PathRow` loses its accordion toggle and becomes a link. *Apply:* extract/reuse `ChapterContents` so both the (now-removed) inline path and the new page share one renderer; `PathRow.onToggle` → navigation. Keep the chapter row's summary (number, title, dates, status, slot_count) as the clickable card. *Decided:* 2026-06-15 (planning).

**D-12: Reconcile with teacher-adjustable-syllabus (#152, shipped mid-build): chapter row navigates in View mode; Edit mode keeps the list-level re-date/reorder/remove/add.** *Rationale:* #152 landed on staging while this feature was in flight, adding an "Edit syllabus" mode (re-date/reorder/remove/add chapters) onto the same expandable accordion that D-8/D-11 replace with a dedicated Chapter Page. They collide in `PathRow`. The user chose to keep BOTH: in **View** mode the chapter row is a navigation `Link` to the Chapter Page (D-8) — no inline accordion; in **Edit** mode (#152's `editing` toggle) the row shows the inline edit controls (date inputs, reorder ↑↓, remove ✕) and does NOT navigate, and "Add chapter" stays. The inline `ChapterContents`/`expanded`/`onToggle` accordion is dropped entirely (the chapter body lives on the page now). *Apply:* `class-syllabus-tab.tsx` `PathRow` renders a `Link` wrapper when `!editing` and the #152 edit row when `editing`; the page (`classes/[cst_id]/page.tsx`) keeps #152's edit-mode state/handlers (`onToggleEdit`/`onSetDates`/`onReorder`/`onRemove`/add) and drops the accordion plumbing (`expandedChapterId`/`onToggleChapter`/`rowCallbacks`/inline timeline). *Decided:* 2026-06-15 (user via AskUserQuestion). *Supersedes the "row stops expanding → becomes a plain link" half of D-11; D-11's reuse-`ChapterContents`-on-the-page half stands.*
