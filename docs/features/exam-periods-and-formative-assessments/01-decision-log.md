# Decision Log

Every architectural decision, indexed `D-N`, with rationale and when decided. **Frozen** once written: to revise, mark the old as "Superseded by D-N+1 on YYYY-MM-DD" and add the new. Never overwrite; both stay. The log grows; don't truncate.

These D-N are local to this feature. References to prior features' decisions are written as `prior D-N (feature-slug)`.

---

**D-1: Exam Periods live in a new `exam_periods` table, scoped to a Syllabus Breakdown.** *Rationale:* exam windows are per-(curriculum, grade, subject) — the same scope as a Syllabus Breakdown — not org-wide like holidays, and the user wants multiple windows ("1–20 Aug, then so on"). A dedicated table mirrors the `syllabus_chapters` shape (FK to the breakdown, a date range, a name) and keeps "exam" semantically distinct from "holiday." *Apply:* migration adds `exam_periods (id, syllabus_breakdown_id FK, start_date, end_date, name)`; all reads filter by `syllabus_breakdown_id`. *Decided:* 2026-06-10 (user, planning).

**D-2: Exam Periods are excluded from teaching-day derivation in BOTH the admin breakdown display AND the teacher's slot projection.** *Rationale:* the user's intent is "exclude those dates from the periods" so the count reflects when LPs can actually be taught. Display-only would still schedule lessons during exams. *Apply:* the dates expanded from a breakdown's Exam Periods are unioned into the `holidays` set passed to `compute_teaching_days` — at the admin `derived_teaching_days` call site AND in the teacher path (`chapter_slot_count` / `project_cst_schedule`). No new exclusion code path; reuse the holiday union. *Decided:* 2026-06-10 (user, planning).

**D-3: The teacher path resolves Exam Periods by matching the CST's (curriculum, grade, subject) to a *published* Syllabus Breakdown.** *Rationale:* the teacher's calendar (`compute_teaching_days` via `chapter_slot_count` and `project_cst_schedule`) keys off the CST, which has no direct breakdown FK; but `resolve_cst_syllabus_context` already finds the published global breakdown for the CST's triple. We reuse exactly that resolution and read its Exam Periods. If there is no published breakdown, the exam-period set is empty (graceful no-op). *Apply:* a helper `get_breakdown_exam_dates(conn, syllabus_breakdown_id) -> set[date]`; teacher call sites resolve the breakdown id (already available in `CstSyllabusContext`) and union its exam dates with effective holidays. *Decided:* 2026-06-10 (planning).

**D-4: Exam Periods are advisory-validated like chapter ranges, not blocking.** *Rationale:* consistent with prior D-5 (chapter-breakdown-and-plan) — date validation warns, never blocks. A chapter date range fully inside an exam period (→ zero teaching days) surfaces as a warning, reusing the existing `compute_range_warnings` "zero_teaching_days" path now that exam dates feed the holiday set. *Apply:* `compute_range_warnings` receives the exam-dates-augmented holiday set; no new warning type required (zero-teaching-days already covers it). Optionally add an `exam_overlap` advisory if a chapter range intersects an exam period — decide at build time, default to relying on zero_teaching_days. *Decided:* 2026-06-10 (planning).

**D-5: Exam Periods are editable only while the breakdown is in `draft`; immutable once `published`.** *Rationale:* mirrors how chapters and the breakdown itself lock on publish (prior behaviour in `router_syllabus`). A published breakdown is the teacher-facing reference; its exam windows shouldn't shift under teachers who've already broken chapters down. *Apply:* exam-period create/update/delete endpoints return 409/422 if the parent breakdown is `published`, same guard the chapter PATCH uses. *Decided:* 2026-06-10 (planning).

**D-6: The Intelligent Chapter Planner decides FA placement inline via a new `slot_type` field on `PlanUnit`.** *Rationale:* the user asked the planner to "decide when to take Formative Assessments" — a pedagogical judgement (after a cluster of related topics, before moving on), not a fixed cadence. Adding `slot_type ∈ ('lesson','formative_assessment')` to the frozen contract lets the LLM choose, keeping the SLO-coverage discipline. *Apply:* extend `PlanUnit` with `slot_type` (default `'lesson'` for back-compat); extend the planner system/user prompts; extend `validate_plan`. *Decided:* 2026-06-10 (user, planning). *Note:* this revises the frozen planner contract — see D-7 for the invariant changes and D-13 for how `period_count` is affected.

**D-7: FA units do NOT consume an `lp_type`; FA units cover topics + SLOs but carry no lesson kind.** *Rationale:* `lp_type` is a lesson-generation concept (reading, grammar, …). An FA is an exam, not a lesson; forcing an `lp_type` onto it is meaningless and would pollute validation. *Apply:* `PlanUnit.lp_type` becomes optional; `validate_plan` requires `lp_type ∈ VALID_LP_TYPES[subject]` **only when `slot_type='lesson'`**, and requires it absent/null when `slot_type='formative_assessment'`. SLO-coverage (every chapter SLO covered ≥1×) counts coverage from BOTH lesson and FA units (an FA covering an SLO still counts as covered). *Decided:* 2026-06-10 (planning).

**D-8: `period_count` still equals the chapter's teaching-day slot count; FAs are slots within it, not extra.** *Rationale:* 1 slot = 1 teaching day is the load-bearing invariant (prior D-9). An FA takes a teaching day like a lesson does. The planner returns exactly `period_count` units total; some are FAs. This keeps the projector's 1:1 day mapping intact and means adding FAs reduces the number of lesson slots, not the calendar length. *Apply:* no change to `chapter_slot_count`; `validate_plan` still requires exactly `period_count` units (lessons + FAs combined). *Decided:* 2026-06-10 (planning).

**D-9: `generate_chapter_plan` persists FA units as `class_assessment_slots` in the same position sequence as lessons.** *Rationale:* lessons and assessments already share one global `position` sequence per CST (the projector merges both tables by position — see `chapter_plan_service.py` lines 313–323). An FA unit at `sequence=k` becomes an assessment slot at the next shared position, preserving day order. *Apply:* in the persist loop, branch on `unit.slot_type`: `'lesson'` → `class_lesson_slots` (+ `class_lesson_slot_topics`) as today; `'formative_assessment'` → `class_assessment_slots` (`assessment_type='formative'`, `book_chapter_id`, `status='scheduled'`) + `class_assessment_slot_topics` for the covered topics. Bump `result.assessment_slot_count`. *Decided:* 2026-06-10 (planning).

**D-10: An FA slot's Exam Generator inputs use a per-subject Default FA Config; no per-slot config UI in this feature.** *Rationale:* the user wants FA slots to "create Exam Generator inputs" the way lesson slots create LP inputs — the inputs must exist and drive generation end-to-end. A full per-slot config editor is a larger surface; a sensible default (short formative quiz per subject) wires the path now and an editable config is a clean fast-follow. *Apply:* constant `DEFAULT_FA_CONFIG[subject] -> Question Config`; a new `get_or_generate_exam_for_assessment_slot(conn, class_assessment_slot_id)` entry point builds an `ExamRequest` (generation_type `'formative'`, the slot's topics' `page_content` + `sub_slo_statements`, `question_config=DEFAULT_FA_CONFIG[subject]`) and dispatches via the existing `generated_exams` service. *Decided:* 2026-06-10 (user, planning). *Partially superseded by D-19 + D-20 on 2026-06-10 (Phase 3 execution):* the real `ExamRequest.generation_type` enum is `{'exam','class_assessment'}` — there is no `'formative'`, so an FA maps to `'class_assessment'` (D-19); and `ExamRequest` has no `sub_slo_statements` field, so they are not sent (D-20). The Default-FA-Config intent and the entry-point design stand.

**D-11: FA exam generation is on-demand from the assessment slot, mirroring `get_or_generate_lp`.** *Rationale:* symmetry with the just-shipped on-demand per-slot LP generation (`get_or_generate_lp`, PR #133). The teacher (or a batch step) triggers exam generation for an FA slot; the service caches on (topic set, config, generation_type) and links `generated_exam_id` back to the slot. *Apply:* new endpoint `POST /api/v2/assessment-slots/{id}/exam` (or extend the class-actions router) calling the D-10 entry point; cache-first via the existing `build_cache_key_global`. *Decided:* 2026-06-10 (planning).

**D-12: No summative-assessment planning in this feature.** *Rationale:* scope control. The user asked specifically for Formative Assessments. `class_assessment_slots.assessment_type` already supports `'summative'`, but the planner emits only `'formative'` here. *Apply:* `PlanUnit.slot_type` allows only `'lesson'|'formative_assessment'`; summative remains future work. *Decided:* 2026-06-10 (planning).* See D-16 for the explicit deferral of full SA support after a scoping discussion.

**D-16: Summative Assessments (SAs) are deferred — an Exam Period is, for now, only a blocked calendar range; SAs are NOT built in this feature.** *Rationale:* a scoping discussion (prompted by the session rename "include FAs and gaps for SA") clarified that an Exam Period is the *window when SAs are taken*, and that SAs are generatable exams whose *results* should be recorded (per-SLO mastery → feeds the downstream dynamic-planner reteach trigger). That is a substantial sub-feature (SA slot creation, summative exam generation, results capture). The user chose to keep this work simple: **just block the Exam Period on the calendar now, and build SAs as a follow-on** ("then we'll go up to building SAs"). *Apply:* Exam Periods remain pure no-teaching exclusion ranges (D-1/D-2) — they create no slots and generate no exams. No `summative` slot creation, no SA results schema. This confirms and extends D-12: summative is out of scope here. The Exam Period table/CRUD/exclusion built in Phase 1 is the foundation the future SA work sits on (SAs will occupy the dates an Exam Period reserves). *Decided:* 2026-06-10 (user, scoping discussion). *Note for the downstream `project-dynamic-chapter-planner` build:* this upstream work delivers FAs + breakdown holidays + exam-period blocking; **SA support (slots, exam generation, per-SLO results) is NOT yet delivered** and must be built before the dynamic planner's SA-driven reteach can rely on it.

**D-13: The `slot_type` contract change is back-compatible — existing callers/tests that omit it get `'lesson'`.** *Rationale:* the `/plan` endpoint and existing planner tests predate `slot_type`. Defaulting to `'lesson'` means a planner response without the field still validates as an all-lesson plan, so nothing breaks before the prompt is updated to emit FAs. *Apply:* `PlanUnit.slot_type: str = Field(default='lesson')`; the LLM prompt is updated in the same phase (Phase 2) so new responses carry it explicitly. *Decided:* 2026-06-10 (planning).

**D-14: The global Syllabus Breakdown also holds general Holidays (Eid, public holidays, breaks) in a `breakdown_holidays` table, and these inherit down to the class plan.** *Rationale:* the user clarified that besides exams, the global plan should carry general non-teaching ranges like Eid that flow into every class plan on that triple. These are conceptually holidays, not exams, so they get their own table (parallel to `exam_periods`, D-1) — keeping the admin UI's two sections clean and the semantics distinct. *Apply:* `breakdown_holidays (id, syllabus_breakdown_id FK, start_date, end_date, name)`, same CRUD + publish-lock (D-5) as exam periods; its expanded dates union into the teaching-day exclusion set exactly like exam dates (D-2/D-3). *Decided:* 2026-06-10 (user message during planning).

**D-15: Breakdown Holidays are distinct from, and additive to, the existing org/school/CST holiday machinery (prior D-26) — they are not migrated into `org_holidays`.** *Rationale:* org holidays are org-scoped (one org, all subjects/grades) and already inherit org→school→CST. Breakdown holidays are (curriculum, grade, subject)-scoped — a different axis. Trying to fold one into the other would force an unnatural scope. Instead both resolve independently and **union** into the final `holidays` set fed to `compute_teaching_days`. A date that's both an org holiday and a breakdown holiday is simply in the set once. *Apply:* the teacher path computes `get_effective_holidays(cst_id) ∪ breakdown_exam_dates ∪ breakdown_holiday_dates`; the admin display uses only the breakdown's own exam + holiday dates. No change to the org-holiday endpoints or resolution. *Decided:* 2026-06-10 (planning, from user message).

**D-18: Both the new FA exam entry point AND the pre-existing `load_assessment_slot_context` resolve curriculum via the org and grade via the class — `class_subject_teachers` has no `curriculum_id` / `grade_id` columns.** *Rationale:* discovered during Phase 3 review: the reused `load_assessment_slot_context` (and the build agent's new pre-read query) joined `curriculums`/`grades` on `cst.curriculum_id` / `cst.grade_id`, columns that do **not** exist on `class_subject_teachers` (it has only `org_id`, `school_class_id`, `subject_id`, …). This was a latent runtime bug — it never fired because `class_assessment_slots` were never populated until Phase 2's FA planner, and the DB-gated tests skip without a seeded DB. *Apply:* both queries now mirror the proven LP path (`generated_lps/service.py::_load_lesson_slot_context`) and `resolve_cst_syllabus_context`: curriculum ← `organizations.curriculum_id` (`JOIN organizations o ON o.id = cst.org_id`), grade ← `school_classes.grade_id` (`JOIN school_classes sc ON sc.id = cst.school_class_id` → `grades g ON g.id = sc.grade_id`), subject ← `cst.subject_id`. Verified no other `cst.curriculum_id`/`cst.grade_id` references remain in the codebase. *Decided:* 2026-06-10 (Phase 3 review, root Claude fixed before PR).

**D-19: An FA exam dispatches with `generation_type='class_assessment'`, not `'formative'`.** *Rationale:* D-10 wrote `'formative'`, but the real `ExamRequest.generation_type` enum (`ug_eg_client.py::_GENERATION_TYPES`) is `frozenset({'exam','class_assessment'})` — `'formative'` would be rejected on construction and would also break the retry path (which re-reads and re-sends `generation_type`). `'class_assessment'` is the semantically-correct existing value for a class-level assessment. *Apply:* `GENERATION_TYPE_FA = 'class_assessment'` in `generated_exams/service.py`; the FA payload and cache key use it. Supersedes the `'formative'` value in D-10. *Decided:* 2026-06-10 (Phase 3 execution; build agent surfaced, accepted — code is ground truth per precedence).

**D-20: FA exams do not send `sub_slo_statements` to UG_EG.** *Rationale:* the glossary listed sub-SLO statements as part of "Exam Generator inputs", but the real `ExamRequest` has no `sub_slo_statements` field — UG_EG derives questions from `page_content` + `question_config`, and per-question→sub-SLO mapping is the downstream tagging service's job (not an input). *Apply:* the FA payload carries `page_content` (joined topic text) + `question_config` (Default FA Config) + `generation_type`; sub-SLO statements are neither loaded nor passed. Supersedes the sub_slo_statements mention in D-10 and the glossary's Exam-Generator-inputs definition. *Decided:* 2026-06-10 (Phase 3 execution; build agent surfaced, accepted).

**D-17: An `lp_type` echoed onto a formative-assessment unit is silently coerced to `None` at parse time, not treated as a fatal plan error.** *Rationale:* the planner has no fallback (prior D-5, intelligent-chapter-planner) — a validation failure rejects the *entire* chapter plan. If the LLM correctly marks a unit `formative_assessment` but cosmetically also echoes an `lp_type`, failing the whole run would be disproportionate to a harmless slip. So `_build_unit` (in `make_chapter_plan`'s parse path) drops the `lp_type` on an FA, producing a clean valid FA. `validate_plan` *still* hard-rejects an FA carrying a non-null `lp_type` as defence-in-depth — that path is only reachable by direct construction / `model_construct` (not via the normal parse), and is exercised by a test. *Apply:* parse-time coercion in `_build_unit`; strict rejection retained in `validate_plan`. If stricter behaviour is ever wanted (fail the plan on any contract violation by the LLM), it's a one-line change to stop coercing in `_build_unit`. *Decided:* 2026-06-10 (Phase 2 execution, build agent surfaced; accepted).
