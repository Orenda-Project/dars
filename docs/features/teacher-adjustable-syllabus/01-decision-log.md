# Decision Log — Teacher-Adjustable Syllabus (suggestion-led)

Frozen architectural decisions. To revise: ask the user, mark old "Superseded by D-N+1 on YYYY-MM-DD", add new referencing the supersession. Both stay.

---

**D-1: The global syllabus is advisory; the class owns its own teaching path. Do NOT reintroduce per-class syllabus scope.** *Rationale:* an earlier draft of this plan forked the global into an editable class-scoped syllabus. The user reframed: the global should only *suggest*; the class records its own real path. So no `scope`/`cst_id` on `syllabus_breakdowns`, no fork-on-edit of a full syllabus. *Apply:* the class path lives in a new `class_chapters` table (D-2); the global stays global + unchanged. *Decided:* 2026-06-03. *Supersedes:* the fork-on-edit approach explored earlier this session (never built).

**D-2: The class's teaching path is a new per-CST table `class_chapters`. Picking a chapter records a row; it does not generate slots.** *Rationale:* the teacher chooses which chapters to teach, in what order, with dates — that choice is first-class state, separate from breaking a chapter down. *Apply:* `class_chapters(id, cst_id, book_chapter_id, position, start_date, end_date, …)`. "Pick a chapter" inserts a row (Action 1). "Break it down" (Action 2) is separate. *Decided:* 2026-06-03 (user: "just records the choice; break down separately").

**D-3: The global default supplies a *recommendation* for the next chapter; the teacher may pick it or any other chapter.** *Rationale:* suggestion-led. At session start (empty path), the app says "nothing planned — the default suggests Chapter 1; what would you like to teach?" with Ch 1 recommended and all chapters selectable. *Apply:* a "recommended next" derivation from the global's order vs. what's already in the class path. *Decided:* 2026-06-03.

**D-4: Chapter status (yet-to-start / in-progress / done) is derived from the chapter's generated class slots.** *Rationale:* status reflects real teaching, not a separate flag to keep in sync. Per chapter (by `book_chapter_id` for the CST): **done** = all its slots terminal (taught/completed/skipped), **in-progress** = some terminal, **yet-to-start** = a path row with no terminal slots (incl. not-yet-broken-down). *Apply:* derived on read in the syllabus/path endpoint. *Decided:* 2026-06-03. *Note:* "done" needs the chapter to have been broken down; a picked-but-unbroken chapter is yet-to-start.

**D-5: "Break it down" (Action 2) reuses the shipped `generate_chapter_plan` unchanged, keyed off a chapter in the class path.** *Rationale:* the period-count → planner → class-slots → show-LPs flow already works (shipped in `syllabus-breakdown-and-teacher-chapter-plan`). Period count = real teaching periods in the chapter's date range (`compute_teaching_days`). *Apply:* break-it-down operates on a `class_chapters` chapter (with the dates from its path row). No new generation logic. *Decided:* 2026-06-03 (user: "reuse existing break-it-down").

**D-6: Reorder is allowed for upcoming (yet-to-start) chapters only; in-progress/done chapters are locked.** *Rationale:* the past is immutable — a chapter with taught history can't be moved or removed; future chapters are freely reorderable. This is what dissolves the half-taught-chapter problem: a partially-taught chapter is just `in-progress` and stays put. *Apply:* reorder/remove endpoints reject changes to non-yet-to-start chapters. *Decided:* 2026-06-03 (user: "order = pick order + can reorder upcoming; lock the taught").

**D-7: Chapters enter the class path UNDATED; the teacher sets each chapter's date range.** *Rationale:* user chose teacher-set dates over copy-from-global. Break-it-down needs a date range (it 422s without one), so the teacher dates a chapter before/at break-down. *Apply:* `class_chapters.start_date/end_date` nullable, set by the teacher. *Decided:* 2026-06-03.

**D-8: What "break it down" GENERATES is out of scope for this feature.** *Rationale:* this feature is the **syllabus** — the class's chapter path (which chapters, order, dates). How a chapter breaks down into LPs/assessments (and any LPs-only vs. assessments question, LLM-driven planning, etc.) belongs to the separate `intelligent-chapter-planner` feature, which owns the `/plan` endpoint's internals. This feature calls `/plan` (Action 2) and is agnostic to whatever it produces. *Apply:* do NOT touch generation/assessment logic here. Earlier drafts of this log had assessment-removal decisions (LPs-only) — removed; that's the other feature's call. *Decided:* 2026-06-03 (user: "you are making the syllabus — why are you concerned with the plan of the chapter?").

## Revival (2026-06-15) — restoring teacher edits after the read-only reversal

Context: PR #109 (2026-06-03) shipped this feature — the full pick/date/reorder/remove mutation layer + editable teacher UI. Days later, `teacher-readonly-syllabus` (PRs #130/#131) **deliberately removed that mutation layer** and made the class syllabus tab read-only ("the class teaching path is set by the school, org-decided, not editable"), keeping only `class_chapters` (the table), the auto-seed, and `list_class_path`. The user has now reversed that reversal: teachers edit their own class's path again. D-1…D-8 stand unchanged; D-9…D-12 record what the revival adds on top of today's staging.

**D-9: Reopen teacher editing of the class path — full pick + set-dates + reorder + remove. Supersedes the `teacher-readonly-syllabus` read-only decision.** *Rationale:* user (2026-06-15): "on the page of the teacher, we want to allow them to edit it as well … edit their dates as well, just like the org lead can. That would change the dates only for that class." When asked to scope, the user chose **full re-date + pick + reorder + remove** — the complete #109 surface, not just dates. The class path is the teacher's again; the global stays advisory (D-1). *Apply:* restore the four mutation endpoints + service functions + editable UI affordances. Per-class only — never touches `syllabus_breakdowns`/`syllabus_chapters` (D-1 still holds). *Decided:* 2026-06-15. *Supersedes:* the `teacher-readonly-syllabus` "org-decided, not editable" decision (which itself was never logged in this folder — it lived in that feature's docs). Restores the D-2/D-3/D-5/D-6/D-7 surface that #109 built.

**D-10: Auto-seed STAYS; the class path is pre-populated from the org's published breakdown on create, and the teacher edits on top. This amends D-3/D-7's "empty path" framing — empty-start is now the fallback, not the primary flow.** *Rationale:* `teacher-readonly-syllabus` added `seed_class_chapters_from_breakdown` (copies the org breakdown's chapters + dates into `class_chapters` on first syllabus read, idempotent, clean-install only). The user explicitly likes this ("the breakdown from ORG is copied to a class. That is perfect"). So the revived flow is: **org breakdown → auto-copied into the class → teacher re-dates / reorders / removes / adds for that class only.** The #109 recommendation-prompt-on-empty-path (D-3) is retained for the genuinely-empty case (no published org breakdown), but is no longer the main entry. *Apply:* keep `seed_class_chapters_from_breakdown` and its call site in the syllabus GET; layer the mutation endpoints on top; the recommendation prompt shows only when the path is empty AND a recommendation exists. *Decided:* 2026-06-15. *Amends (does not supersede):* D-3, D-7 — both still describe the empty-path/teacher-set-dates mechanics, which remain correct; D-10 reframes which path is primary.

**D-11: `remove_chapter` rejects a chapter that has ANY generated class slots, not just terminal ones — and never silently orphans dynamic-planner slots.** *Rationale:* since #109, the dynamic-chapter-planner (PR #143) added `origin` (`breakdown`/`reteach`/`manual`), `reteach_for_sub_slo_id`, and `flex` columns to the slot tables. #109's `remove_chapter` deleted the `class_chapters` row without touching slots, relying on the D-6 status-lock (only `yet_to_start`, i.e. no *terminal* slots, is removable). But a chapter can now hold non-terminal generated slots (a fresh break-down, or a reteach insert) that aren't terminal yet — deleting the path row would orphan them. *Apply:* `remove_chapter` raises 422 if the chapter has *any* row in `class_lesson_slots`/`class_assessment_slots` for that `(cst_id, book_chapter_id)` — message: "this chapter has a generated plan; clear it before removing." (Removal stays a yet-to-start, not-yet-broken-down operation.) Reorder is unaffected — it only rewrites `position` and the new slot columns have safe defaults. *Decided:* 2026-06-15.

**D-12: Restore the #109 code as the baseline, but graft the editable UI onto today's expandable syllabus tab rather than reverting the file.** *Rationale:* the backend service/endpoints/schemas that #109 added and #130/#131 removed can be lifted near-verbatim from commit `91e1763` (modulo D-11). The frontend cannot: the syllabus tab was reworked twice after #109 (PR #147 made chapter rows expandable to their LPs/assessments and dropped the Timeline tab; PR #148 fixed slot visibility). Reverting `class-syllabus-tab.tsx` to #109 would lose the expand-to-contents UX. *Apply:* keep the current expandable `PathRow`; add inline date inputs (onBlur → `setChapterDates`), reorder ▲▼ (disabled when status≠yet_to_start), a remove ✕ (disabled unless yet_to_start AND not generated, per D-11), and an "add a chapter" affordance using the recommendation + a book-chapter picker. The page (`[cst_id]/page.tsx`) regains the `handlePick/handleSetDates/handleReorder/handleRemove` + `runPathMutation` wiring from #109. *Decided:* 2026-06-15.

**D-13: Editing is gated behind an explicit "Edit syllabus" toggle on the cloned class breakdown — not always-on inline controls.** *Rationale:* user (2026-06-15): "I want there to be an edit button on the [breakdown] already cloned from the org's breakdown … then the teacher can edit that breakdown to their own dates." The default view is the cloned breakdown shown as-set (dates as plain text, no controls) — it reads as a settled plan the teacher received from the org. Clicking **Edit syllabus** flips the tab into edit mode, revealing per-chapter date inputs, reorder ▲▼, remove ✕, and the add-a-chapter affordance (the D-12 controls). A **Done** button exits edit mode back to the clean read view. This keeps the everyday "look at my plan / break a chapter down" path uncluttered and makes editing a deliberate act. *Apply:* `class-syllabus-tab.tsx` gets an `editing` UI state (lifted to the page or local to the template per webapp layering — template stays prop-driven, so the page owns the boolean + passes `editing` + `onToggleEdit`). Expand-to-contents (view LP, mark-taught, generate, break-it-down) stays available in BOTH modes — edit mode only *adds* the path-mutation affordances; it doesn't hide the slot rows. *Decided:* 2026-06-15.

**D-14: Confirmed — "we break down" is the existing Action 2 (teacher triggers, system generates), unchanged.** *Rationale:* user (2026-06-15): "Then they breakdown and we breakdown" → on clarification, "Teacher triggers, system generates." The teacher edits dates (Action 1), then clicks "Break it down" on a chapter, and the system runs the already-shipped `generate_chapter_plan` (`/plan`) to produce that chapter's slots — sized by the (now teacher-edited) class-path date range. No new or second break-down mechanism. *Apply:* nothing new — D-5/D-8 already cover this; the break-it-down button stays as shipped, now reachable from both view and edit modes (D-13). What it generates remains `intelligent-chapter-planner`'s domain (D-8). *Decided:* 2026-06-15.

**D-15: This revival is developed in its OWN branch + git worktree, isolated from `lp-context-header`; the two are not coupled and neither waits on the other.** *Rationale:* user (2026-06-15), on the `class-syllabus-tab.tsx` collision: "your work should be in a different branch. in separate worktrees." Both features touch the same file but evolve independently; whichever merges to staging first, the second rebases and resolves the overlap at merge time (standard per dars/CLAUDE.md worktree rule). No combined PR (rejects the "merge the two efforts" option), no blocking wait (rejects "land lp-context-header first" as a hard gate). *Apply:* branch `feat/teacher-adjustable-syllabus-revival` in worktree `.claude/worktrees/teacher-adjustable-syllabus-revival`; one PR → staging. The collision note in `05-phase-3-revival.md` still governs *how* F3.4 adapts at execution time depending on which frontend structure is on staging when this branch is built (accordion → graft on accordion; Chapter Page already merged → put edit affordances on the Chapter Page). *Decided:* 2026-06-15.
