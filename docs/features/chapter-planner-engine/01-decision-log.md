# Decision Log — Chapter Planning Engine (v2 standalone)

Frozen architectural decisions. To revise: ask the user, mark the old entry "Superseded by D-N on YYYY-MM-DD", add the new one referencing the supersession. Never overwrite; both stay. The log grows — don't truncate.

Format: **D-N: decision.** *Rationale:* why. *Apply:* where/when. *Decided:* date/PR.

---

**D-1: CPE is a standalone FastAPI service modeled on `UG_LessonPlan`/`UG_EG`, living at `dars/chapter-planner-app/`.** *Rationale:* The user wants an independent, iterable app (its own `main.py`, `config.py`, `llm_client`, `prompts/`, `services/`, static playground), not code wired into the dars backend. Keeping it inside `dars/` (vs a top-level `UG_ChapterPlan`) keeps it in the repo and branch the user is working in. It is NOT imported by the dars FastAPI app and shares no process with it. *Apply:* New directory `dars/chapter-planner-app/`. No import edges from `dars/server/` into it. *Decided:* 2026-06-03 (planning, user direction).

**D-2: The planner is LLM-only; no deterministic fallback.** *Rationale:* Mirrors the lesson learned in the in-dars `intelligent-chapter-planner` (its D-16): the deterministic fallback produced mechanically poor plans and hid backend failures. CPE's entire purpose is LLM reasoning about LP boundaries and SLO coverage. A malformed/invalid plan fails the request loudly. *Apply:* The planner calls `PlannerLLM`, parses strict JSON, runs `PlanValidator`; on LLM error or any validation violation it raises a 4xx/5xx — no fallback path exists. *Decided:* 2026-06-03 (planning).

**D-3: v2 uses the Agents-SDK (`claude-agent-sdk`) OAuth backend exclusively.** *Rationale:* The user wants to iterate locally against their Claude Code OAuth session with zero console API spend while building. Because CPE is not in production this round, no API-key backend is needed yet. (Production credentialing will be decided when CPE replaces the dars deterministic path — see D-9.) *Apply:* `PlannerLLM` protocol `async complete(system, user) -> str`. One impl this round: `AgentSdkPlannerLLM` wrapping `claude-agent-sdk` — iterate `message.content[].text`, construct a `ClaudeAgentOptions(system_prompt=...)` (learned from the in-dars planner's D-13 bug). `claude-agent-sdk` is a service dependency for v2. Tests inject a fake `PlannerLLM`. *Decided:* 2026-06-03 (planning, user direction).

**D-4: A Plan Unit may merge ≥2 Topics or split one Topic across units — the LLM decides boundaries.** *Rationale:* Same reasoning as the in-dars planner's D-2: thin adjacent topics waste a period if forced apart; a dense topic may need two units. The LLM owns boundary decisions, then attaches the relevant SLOs to each unit. *Apply:* `PlanUnit.topic_ids` is an ordered list (≥1); `PlanUnit.slo_ids` (≥1) are the SLOs that unit targets. `topic_text` is the concatenation (in `topic_ids` order) of the member topics' text. *Decided:* 2026-06-03 (planning).

**D-5: `lp_type` is exclusively the LLM's choice, constrained to `VALID_LP_TYPES[subject]`.** *Rationale:* Mirrors the in-dars planner's D-15 — `recommended_lp_type` data is too sparse to drive selection, and the LLM reasons lp_type well from topic text + SLO statements. *Apply:* The prompt passes the subject's allowed lp_type list; the LLM picks one per unit. `PlanValidator` rejects any lp_type not in `VALID_LP_TYPES[subject]`. The allowed lists are copied verbatim into CPE config from UG_LP (see [06-reference-ug-lp-input.md](06-reference-ug-lp-input.md)). *Decided:* 2026-06-03 (planning).

**D-6: FA / assessments are out of scope for v2 — CPE emits only LP Plan Units.** *Rationale:* User explicitly scoped to "ignore assessments for now; N periods → N LPs". *Apply:* No FA items in the `ChapterPlan` schema. Revisit when assessment planning is requested. *Decided:* 2026-06-03 (planning).

**D-7: The output Plan Unit is a direct, lossless input to UG_LessonPlan's `/generate-lp`.** *Rationale:* CPE plans *which* LPs to make; the next step feeds each unit to UG_LP. Designing the unit to map 1:1 onto `LPGenerationRequest` (subject, grade, `lp_type`, `page_content`=`topic_text`) means no translation layer is ever needed — and makes the eventual dars replacement (D-9) clean. *Apply:* `PlanUnit` fields are named/shaped so a thin adapter builds an `LPGenerationRequest` with no missing data. The reference doc 06 is the frozen target shape. *Decided:* 2026-06-03 (planning).

**D-8: `PlanValidator` is a pure function gating every plan; failure fails the request (no repair, no fallback).** *Rationale:* The LLM can hallucinate topic/SLO IDs, miscount units, or emit an invalid lp_type. *Apply:* Invariants: (a) `len(units) == period_count`; (b) every chapter SLO id appears in ≥1 unit's `slo_ids`; (c) every unit's `lp_type ∈ VALID_LP_TYPES[subject]`; (d) every unit has ≥1 topic_id and ≥1 slo_id, all referencing real chapter topics/SLOs; (e) `sequence` values are a permutation of `1..period_count`. Any violation → raise with the reason; the request fails. *Decided:* 2026-06-03 (planning).

**D-9 (forward-looking, not implemented in v2): CPE will eventually replace the dars deterministic `make_chapter_plan` path.** *Rationale:* User intent stated at planning time. *Apply:* Out of scope for v2 (CPE stays standalone). When undertaken: re-decide the production LLM credential (API-key, not OAuth/Agents-SDK — OAuth is dev-only per D-3), and the integration becomes a new feature with its own folder. The dars `intelligent-chapter-planner` decision log is the reference for the path being replaced. *Decided:* 2026-06-03 (planning, user direction).
