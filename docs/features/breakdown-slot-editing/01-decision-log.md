# Decision log — Breakdown Slot Editing

Decisions are frozen once recorded. If a later decision overrides an earlier one, the earlier entry stays and is amended with "Superseded by D-N+1 on YYYY-MM-DD"; both stay in the log.

References to D-N in the v2 rebuild's [01-decision-log.md](../../plans/2026-05-15-dars-v2-rebuild/01-decision-log.md) are prefixed `v2-D-N` to disambiguate.

---

**D-1: Editing is per-slot, not per-run.** *Rationale:* the existing UI groups consecutive identical slots into a "Days N–M" run for browsability, but each row is still backed by a single `breakdown_slots` record. Editing a run as a unit would require splitting it server-side; we don't need that complexity in v1. The side panel addresses one slot at a time. *Apply:* the side-panel form binds to the selected slot; runs are still rendered grouped but each slot inside an expanded run is selectable individually. *Decided:* 2026-05-20.

**D-2: One PATCH per save (not per field).** *Rationale:* the backend `BreakdownSlotUpdate` accepts every editable field as optional, so a single PATCH can change `slot_type` + `lp_type` + `topic_id` atomically. Per-field PATCHes would race on quick edits and require N round trips. *Apply:* side panel holds local form state; "Save" sends one PATCH; "Cancel" reverts; if a field is unchanged we omit it from the body. *Decided:* 2026-05-20.

**D-3: `slot_type` and `lp_type` are coupled in the UI.** *Rationale:* the backend's `_validate_slot_inputs` rejects illegal combos (e.g. assessment slots must have `lp_type=null`; lesson slots must have a subject-valid `lp_type`). Surfacing this as a single dropdown of legal `(slot_type, lp_type)` combos prevents 422s on save. *Apply:* the UI builds a flat option list per subject from `LP_TYPES_BY_SUBJECT` + `VALID_SLOT_TYPES`; assessments render as `slot_type=formative_assessment, lp_type=null`; lessons render as `slot_type=lesson, lp_type=<X>`. Server still validates as last line of defense. *Decided:* 2026-05-20.

**D-4: Topic dropdown is scoped to the slot's chapter.** *Rationale:* the backend rejects a `topic_id` whose chapter is not in the breakdown (`topic_id belongs to a chapter not present in this breakdown`). Restricting the dropdown to topics from the slot's *own* chapter matches the natural mental model (a slot teaches part of its chapter) and avoids the 422. Cross-chapter topic moves require relocating the slot to a different `breakdown_chapter_id` first, which is out of scope here. *Apply:* `GET /api/v2/topics?book_chapter_id=<X>` populates the dropdown; X is the slot's `breakdown_chapter.book_chapter_id`. *Decided:* 2026-05-20.

**D-5: Add/Delete slot is per chapter, not at the top level.** *Rationale:* every slot belongs to a `breakdown_chapter`, and `position` (breakdown-wide) plus `chapter_position` (within-chapter) must stay consistent. Restricting "Add slot" to the chapter header means we already know the chapter, and we can compute the new positions ourselves (append: `max(position)+1` for breakdown, `max(chapter_position)+1` for chapter). *Apply:* each chapter header gets an "+ Add slot" button (draft only); deleting a slot is from the side panel's "Delete" button. After add/delete we reload the breakdown to get the server's new state. *Decided:* 2026-05-20.

**D-6: No "shift everything down" on add.** *Rationale:* inserting a slot in the middle of a 180-slot breakdown would force renumbering of every slot after it (because of the UNIQUE constraint on `(breakdown_id, position)`). For v1 we skip mid-insertion entirely — "Add slot" appends at the end of the chapter (and at the end of the breakdown). Re-ordering is explicitly deferred. *Apply:* "Add slot" appends only; no insert-before-slot affordance. If the user needs to insert in the middle, they delete tail slots, add new ones in order, and rebuild from there. *Decided:* 2026-05-20.

**D-7: Class-scope breakdowns are not editable here.** *Rationale:* this feature is "client edits their org breakdown." Class-scope breakdowns are derived (forked + realized) from the org-scope one. v2-D-23 keeps overrides at the org level. The backend's `_require_draft` still allows draft class breakdowns to be PATCHed, but exposing that affordance in the dashboard is out of scope. *Apply:* the editor checks `data.scope === "org"` (not just `editable && anchorAllowed`); if the breakdown isn't org-scope, edit affordances stay hidden. *Decided:* 2026-05-20.

**D-8: Published breakdowns remain immutable in the UI.** *Rationale:* v2-D-18 already specifies that PATCH on a published breakdown creates a new draft version server-side. Triggering that flow accidentally from a slot edit would be surprising. The UI does not call PATCH against a published breakdown's slot endpoints. To edit a published breakdown the admin clicks an explicit "Edit (create new version)" button at the breakdown top, which calls `PATCH /breakdowns/{id}` with a trivial body to fork a new draft. That button is **out of scope** for this PR — for now, if a breakdown is published, the side panel is read-only as it is today. *Apply:* the editable predicate stays `data.status === "draft"`; nothing else needs to change. The "edit published" button is a follow-up. *Decided:* 2026-05-20.

**D-9: Edits to an org breakdown do not propagate to already-forked class breakdowns.** *Rationale:* per v2-D-18, class-scope breakdowns are flat deep-copies of the org breakdown at fork-time (`fork_service.py` copies every chapter + slot into new rows; `parent_breakdown_id` is a lineage pointer, not a propagation channel). Already-forked classes are structurally unreachable from the org slot CRUD endpoints — different `breakdowns.id`, different `breakdown_slots` rows, no FK that cascades. This is the *intended* behavior: teachers don't get their plan rewritten under them mid-year. Only a CST whose class breakdown is created (or replaced via delete+refork) **after** the org edits publish will pick up the new plan. *Apply:* this PR does NOT add any "push this update to existing classes" affordance. If a future feature wants that, it goes through a deliberate "republish-and-cascade" flow with explicit per-class opt-in, not as a side effect of slot editing. *Decided:* 2026-05-20.
