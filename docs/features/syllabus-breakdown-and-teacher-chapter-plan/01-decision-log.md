# Decision Log — Syllabus Breakdown & Teacher Chapter Plan

Frozen architectural decisions. To revise: ask the user, mark old "Superseded by D-N+1 on YYYY-MM-DD", add new referencing the supersession. Both stay.

---

**D-1: Rename "Chapter Breakdown" → "Syllabus Breakdown" everywhere** (docs, code, UI, API copy, feature/persona docs). *Rationale:* user's vocabulary; "syllabus" better conveys the whole-book chapter-timing artifact vs. the per-chapter plan. *Apply:* Phase 1, pervasive. *Decided:* 2026-06-02.

**D-2: The Syllabus Breakdown is the ONLY admin/global breakdown artifact, and holds chapter→date-range only (no slots).** *Rationale:* clean separation — admin owns *when chapters happen*, teacher owns *what happens inside a chapter*. *Apply:* `breakdowns` keeps **global scope only**; `breakdown_chapters` keeps `book_chapter_id, position, start_date, end_date` (drop `teaching_days` — derived). Drop `breakdown_slots` + `breakdown_slot_topics` entirely. *Decided:* 2026-06-02.

**D-3: Drop org/class breakdown scope and the entire fork chain.** *Rationale:* with no slots at admin scope and chapter plans being teacher-generated, there is nothing meaningful to fork; teachers consume the global Syllabus Breakdown for their class directly. *Apply:* delete `fork_service.py`, fork-org/fork-class endpoints, org/class scope handling. `breakdowns.scope` is effectively always `global`. *Decided:* 2026-06-02.

**D-4: The Chapter Plan is a teacher-only feature in the teacher app.** *Rationale:* the teacher knows their real timetable; the plan must reflect their actual periods. *Apply:* no admin/dashboard slot authoring. The "break it down" action lives in `/teacher-app`. *Decided:* 2026-06-02.

**D-5: Remove realization (`realize_service.py`) and auto-build (`auto_build_service.py` whole-book + `seed_chapter_slots`).** *Rationale:* realization copied `breakdown_slots`→class slots; with slots gone from admin scope, the class slots are now teacher-generated instead. Auto-build built whole-book slot sequences at admin scope — no longer needed. *Apply:* delete both services + their endpoints (auto-build endpoint, seed_chapter endpoint, publish-triggered realize). *Decided:* 2026-06-02. *Salvage:* see D-12.

**D-6: Keep the class slot tables (`class_lesson_slots`, `class_assessment_slots`, `class_assessment_slot_topics`), repurposed.** *Rationale:* the teacher app (timeline, today, mark-taught, LP/exam detail) is wired to these; rewriting that layer is needless churn. *Apply:* same tables, now populated by the teacher's break-it-down action, not realization. Drop the `breakdown_slot_id` FK column (no longer sourced from breakdown_slots). *Decided:* 2026-06-02.

**D-7: Rename the DB tables to `syllabus_breakdowns` / `syllabus_chapters` — consistent naming everywhere, table layer included.** *Rationale:* user explicitly wants consistent naming end-to-end ("I really need consistent naming everywhere"). Since all operational data was wiped (2026-06-02) and slots are being dropped anyway, there is no data to migrate — the migration drops the old tables and creates clean syllabus-named ones. Endpoints become `/syllabus-breakdowns/...`, schemas `Syllabus*`, UI "Syllabus Breakdown". *Apply:* Phase 2 migration creates `syllabus_breakdowns` (was `breakdowns`, global-only) + `syllabus_chapters` (was `breakdown_chapters`: id, syllabus_breakdown_id, book_chapter_id, position, start_date, end_date). Drop `breakdowns`, `breakdown_chapters`, `breakdown_slots`, `breakdown_slot_topics`. *Decided:* 2026-06-02 (user chose full table rename over keeping names — SUPERSEDES the original "keep names" wording). *Note:* the global Syllabus Breakdowns currently in staging (2 published, built 2026-06-02) will be dropped by this migration and must be re-created via the auto-build-style direct insert against the new tables (Phase 2 includes re-seeding them).

**D-8: Keep the timetable/holiday/projector machinery as-is** (`timetables`, `org_holidays`, overrides, `projector.py`, `holidays.py`). *Rationale:* independent of slots; reused for both the slot-count formula and dating the teacher's generated slots. *Apply:* no change except reuse. *Decided:* 2026-06-02.

**D-9: Slot count for a chapter = the count of real teaching periods in the chapter's date range.** *Rationale:* what matters is the actual number of teaching periods between the chapter's start and end dates — NOT a `periods/week × weeks` approximation (which rounds badly on partial weeks). The weekly timetable (Mon/Tue/Wed…) is just the *input* telling us which weekdays are teaching days. So: `slot_count = len(compute_teaching_days(chapter.start_date, chapter.end_date, cst_timetable_weekdays, effective_holidays))`. This is **exactly** the existing `projector.compute_teaching_days` — same calendar used to date slots — so generated slots map 1:1 onto the dates the teacher actually teaches. *Apply:* Phase 3, F3.2. *Decided:* 2026-06-02 (revised from the original ×weeks formula in the same conversation, before any code). *Superseded original wording:* the ×weeks framing was dropped; this is the canonical definition.

**D-14: Holidays reduce the slot count.** *Rationale:* a chapter spanning a holiday week should produce fewer slots — true teaching capacity. Use the full `get_effective_holidays(cst_id)` (org + school + CST overrides) as the holidays set passed to `compute_teaching_days`. *Apply:* Phase 3, F3.2. *Decided:* 2026-06-02.

**D-10: The teacher app positions the syllabus by today's date** — highlights the chapter whose date range contains today (or the next upcoming one). *Apply:* Phase 3 teacher-app view. *Decided:* 2026-06-02.

**D-11: The data bank is not touched.** *Rationale:* explicit user instruction — curriculums, grades, subjects, slos, sub_slos, books, book_chapters, topics, mappings, and the global Syllabus Breakdowns survive. *Apply:* all phases — demolition is scoped to slots/fork/realize/auto-build only. *Decided:* 2026-06-02.

**D-12: Salvage the pure planners from `auto_build_service.py` (`allocate_chapter_days`, `plan_chapter_slots`, `pick_lp_type`) into a teacher-side service; delete the rest of auto-build.** *Rationale:* these are tested, pure functions that distribute lessons/FAs/SAs/revision across N slots and pick lp_type per topic — exactly what break-it-down needs. Don't reinvent. *Apply:* Phase 3 — move planners to e.g. `chapter_plan_service.py`; the whole-book orchestration + DB inserts of auto-build are deleted. *Decided:* 2026-06-02.

**D-13: This re-architects the shipped `chapter-breakdown-and-plan` feature.** Phase 1 of that feature (chapter date ranges, `chapter_calendar.py` derived-days) is kept + renamed. Phase 2 (admin page ranges, manual slot builder, per-chapter seed) is removed from admin scope; the page-range concept (`page_start`/`page_end`) **moves to the teacher's class slots** (kept — D-15). *Apply:* mark that feature superseded in its onramp. *Decided:* 2026-06-02.

**D-16: Class slots gain a direct `book_chapter_id` column (their chapter link).** *Rationale:* the timeline grouped slots by chapter via the now-dropped `breakdown_slots`→`breakdown_chapters` join (this broke `get_cst_timeline` in Phase 2 — a dangling reference). In the teacher-generated model, each class slot belongs to the chapter it was generated from. Add `book_chapter_id UUID REFERENCES book_chapters(id)` to `class_lesson_slots` + `class_assessment_slots`; "break it down" stamps it; the timeline joins `book_chapters` directly for chapter id/position/title. Nullable (legacy rows / safety), but always set by generation. *Apply:* Phase 3 migration `20260605000000_class_slots_book_chapter.sql` + F3.3 generation + timeline rewrite. *Decided:* 2026-06-02.

**D-15: The teacher Chapter Plan keeps page ranges (`page_start`/`page_end`) on the class slots — for now.** *Rationale:* user confirmed keep page ranges for now. Added to `class_lesson_slots` / `class_assessment_slots` in Phase 3. *Forward note (later focus, not now):* the Chapter Plan breakdown module will be reworked later to produce the exact structured outputs that feed LP Assistant + the assessment generator inputs. Page ranges are a step toward that, but the full input contract is explicitly deferred. *Apply:* Phase 3 (page-range columns); future feature for the LP/assessment input contract. *Decided:* 2026-06-02.
