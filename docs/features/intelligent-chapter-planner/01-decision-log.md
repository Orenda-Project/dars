# Decision Log — Intelligent Chapter Planner

Format: **D-N: decision.** *Rationale:* why. *Apply:* where/when. *Decided:* date/PR.

---

**D-1: Build a new LLM-driven Chapter Planner as the primary path; keep the existing deterministic algorithm as a fallback.** *Rationale:* The current `allocate_chapter_days`/`plan_chapter_slots`/`pick_lp_type` is mechanical (proportional days, fixed FA cadence, keyword lp_type) — the user wants real reasoning about difficulty, LP boundaries, and assessment coverage. A fallback means an LLM outage or a malformed response never blocks a teacher from breaking down a chapter. *Apply:* `chapter_planner_service.py` (new) is called first inside `generate_chapter_plan`; on unavailability/invalid output it falls through to the salvaged pure planners. *Decided:* 2026-06-03 (planning).

**D-2: An LP unit is an LLM-defined teaching unit, not 1:1 with a book topic.** *Rationale:* Thin adjacent topics waste a period each if forced to separate LPs; a dense topic may need two. The LLM decides LP boundaries — it may merge ≥2 topics into one LP or split one topic across two LPs — then attaches the relevant sub-SLOs. *Apply:* `PlanItem` LP units carry an ordered `topic_ids` list (≥1) plus `sub_slo_ids`. Persistence uses the join table (D-4). The deterministic fallback still emits one-topic LP units (it can't reason about merging) — that's acceptable for a fallback. *Decided:* 2026-06-03 (planning).

**D-3: A PlanValidator gates every LLM plan; failure routes to the deterministic fallback.** *Rationale:* The LLM can hallucinate topic IDs, miscount periods, or emit an invalid lp_type. Rather than partially trust output, we validate against hard invariants and fall back wholesale on any failure — one code path for "trusted plan". *Apply:* `PlanValidator` (pure) enforces: (a) item count == period count; (b) every chapter topic appears in ≥1 LP unit's `topic_ids`; (c) every LP unit's `lp_type` passes `is_valid_lp_type(subject, lp_type)`; (d) every LP unit has ≥1 topic and ≥1 sub-SLO; (e) every FA item's `sub_slo_ids`/`topic_ids` ⊆ the chapter's sub-SLOs/topics; (f) ≥1 LP unit and (if periods permit) ≥1 FA item — "periods permit" threshold fixed at `period_count > 5` by D-11. Validation failures log at WARNING with the reason and increment a fallback counter in logs. *Decided:* 2026-06-03 (planning).

**D-4: Multi-topic LP units persist via a new `class_lesson_slot_topics` join table, mirroring `class_assessment_slot_topics`.** *Rationale:* `class_lesson_slots.topic_id` is a single FK; an LP unit spanning topics can't be represented relationally. A join table keeps the linkage queryable and matches the existing assessment-coverage pattern. `class_lesson_slots.topic_id` is retained as the **primary topic** (first in the ordered list) for back-compat with the existing LP cache/dispatch keyed on `topic_id`. *Apply:* See `02-data-model.md`. Migration is additive (new table); `topic_id` column unchanged. *Decided:* 2026-06-03 (planning).

**D-5: The LLM decides FA count, placement, and coverage in the same planning call.** *Rationale:* FA pacing is part of the same pedagogical reasoning as LP sequencing — splitting it across a fixed cadence + a separate coverage call would fragment the plan. One call yields one coherent `ChapterPlan`. *Apply:* The planner prompt asks for the full ordered sequence including FA items; the LLM chooses how many FAs and where. Validator only enforces coverage ⊆ chapter and the period-count invariant — it does not impose a cadence. *Decided:* 2026-06-03 (planning).

**D-6: Summative assessments are out of scope this round; the planner emits only LP units and FA items.** *Rationale:* User explicitly scoped to FA + LPs. *Apply:* No SA items in `ChapterPlan`. The deterministic fallback is called with `sa_per_chapter=0` so both paths agree. (Today's default is `sa_per_chapter=1`; the planner overrides it to 0 — see scope note in phase docs.) Revisit when SA planning is requested. *Decided:* 2026-06-03 (planning).

**D-7: Wire behind the existing `/plan` endpoint; no new API surface or UI this round.** *Rationale:* User chose "backend planner only". The endpoint contract, persistence tables, and downstream LP/FA generation are unchanged — the planner is a drop-in replacement for the planning step inside `generate_chapter_plan`. *Apply:* `POST /csts/{cst_id}/chapters/{book_chapter_id}/plan` keeps its request/response shape. No preview/dry-run endpoint (that was option B/C, not chosen). *Decided:* 2026-06-03 (planning).

**D-8: The LLM client reuses the existing breakdown LLM wrapper (Anthropic), not a new provider.** *Rationale:* `dars/breakdown` already has an async Anthropic wrapper (`call_llm`) used by the sub-SLO breakdown engine; reuse keeps one LLM dependency and one config path. *Apply:* The planner calls that wrapper (or a thin sibling in the same module) with a strict-JSON system prompt. Model choice follows the existing breakdown config. *Decided:* 2026-06-03 (planning). **Superseded by D-10 on 2026-06-03** (the planner now goes through a `PlannerLLM` interface with two backends; the API-key backend wraps this wrapper for production).

**D-10: The planner calls Claude through a `PlannerLLM` interface with two swappable backends — API-key for production, Agents SDK for development.** *Rationale:* The user wants the production endpoint to use the supported server-side credential (`ANTHROPIC_API_KEY`, already configured on Railway), but to develop/iterate on the planner locally using the Agents SDK (`claude-agent-sdk`) against their Claude Code OAuth session — avoiding console API spend during development and getting the SDK's ergonomics while building. A single interface keeps both paths producing the same `str` JSON output the parser expects. OAuth-via-SDK is acceptable for **local development only** (interactive, per-developer); it is never the production credential (subscription/OAuth tokens aren't licensed for backend service traffic). *Apply:* Define `PlannerLLM` protocol: `async complete(system: str, user: str) -> str`. Two impls: (a) `ApiKeyPlannerLLM` wrapping `breakdown/llm_client.call_llm` (the D-8 wrapper) — **the only backend used in production**; (b) `AgentSdkPlannerLLM` wrapping `claude-agent-sdk`, used when a dev env flag is set (e.g. `PLANNER_LLM_BACKEND=agent_sdk`). Selection is config-driven in `dars.config.settings`; production config never sets the SDK backend. `make_chapter_plan`/`plan_with_llm` (F-1.3) take the injected `PlannerLLM`; tests inject a fake. `claude-agent-sdk` is added as a **dev/optional dependency**, not a runtime production dependency — the import is lazy so production never requires it installed. *Decided:* 2026-06-03 (planning).

**D-9: The LP cache key gains a topic-set dimension so multi-topic LP units don't collide with single-topic cache entries.** *Rationale:* `generated_lps` caches global lesson LPs by `(curriculum, topic_id, lp_type)`. A multi-topic LP unit covering topics {A,B} is a different lesson than single-topic LP for A, yet would collide on `topic_id=A`. *Apply:* When an LP unit has >1 topic, dispatch uses a **class-scoped** generation (the existing class-scope branch in `generated_lps/service.py` already handles topic combos the global breakdown didn't have — D-56/D-57 of the syllabus feature), keyed by a hash of the ordered topic set. Single-topic LP units keep the existing global cache key unchanged. No new migration needed — the class-scope path exists. *Decided:* 2026-06-03 (planning). *Note:* verify the class-scope keying covers the multi-topic case during Phase 2; if it keys only on a single `topic_id`, extend it then and log a follow-up decision.

**D-12: The class-scope LP cache key is extended to hash the LP unit's *ordered topic set* (resolves the D-9 follow-up).** *Rationale:* D-9 mandated multi-topic LP units route through the existing class-scope branch in `generated_lps/service.py`, and noted the keying had to be verified during Phase 2. On inspection the class-scope path (`get_or_generate_class_specific_lp` / `_build_cache_key_class`) keyed only on the single primary `topic_id` (`{curriculum}:{cst}:{topic_id}:{lp_type}`), loaded `page_content` from one topic, and unioned sub-SLOs from one topic. Two distinct multi-topic units sharing the same primary topic (D-4) would collide, and `page_content` would omit the merged topics. *Apply:* Added `_build_cache_key_class_topic_set(curriculum_id, cst_id, topic_ids, lp_type)` → `{curriculum}:{cst}:set:{sha256(ordered topic_ids)}:{lp_type}` and a `_load_lesson_slot_topic_set` reader over the new `class_lesson_slot_topics` join (D-4). When a slot has >1 join-table topic, `get_or_generate_class_specific_lp` uses the topic-set key, concatenates the topics' `topic_text` in `position` order as `page_content` (`"\n\n".join(...)`), and unions their sub-SLOs (`_load_union_topic_sub_slos`) into `sub_slo_statements`. Single-topic / legacy slots (no join rows) keep the original `_build_cache_key_class` behaviour unchanged. The hash uses insertion order (not sorted) because order is pedagogically meaningful for a merged lesson — distinct from the revision path's sorted `_hash_topic_id_list`. No migration (the class-scope path and the join table already exist). *Decided:* 2026-06-03 (Phase 2 execution, F-2.5).

**D-11: Validator invariant (f) "FA expected" threshold = `period_count > 5` (the FA cadence); revision and sub-SLO mappings for the fallback fixed as below.** *Rationale:* Phase 1 (F-1.4) requires the deterministic fallback to always pass its own validator (D-3), but the salvaged `allocate_chapter_days` only emits an FA once lesson periods reach `fa_cadence` (=5) — so genuinely short chapters (≤5 periods) produce zero FAs. Invariant (f) as worded in D-3 ("≥1 FA item when periods permit") was ambiguous about the threshold; left literal it would fail the fallback on small chapters. Resolved toward fallback self-consistency. *Apply:* In `validate_plan`, only require ≥1 FA item when `period_count > 5`. Also frozen during F-1.4 mapping: (1) a deterministic **revision** slot maps to an LP unit with `lp_type='revision'` covering all chapter topics/sub-SLOs ('revision' is valid for every subject, keeping the fallback validator-clean — doc 05 has no separate revision kind); (2) a fallback LP unit's `sub_slo_ids` = the sub-SLOs mapped to its topic; an FA item's `sub_slo_ids` = the union of its covered topics' sub-SLOs. *Decided:* 2026-06-03 (Phase 1 execution). *Note:* `period_count > 5` couples the validator to `fa_cadence=5`; if the LLM path later wants FAs on shorter chapters, this only governs whether the validator *rejects* an LLM plan for lacking an FA — the LLM may still add one. Revisit if `fa_cadence` becomes configurable.

**D-13: Fix the `AgentSdkPlannerLLM` dev backend — collect text from content blocks and pass `ClaudeAgentOptions`.** *Rationale:* A live dry-run (Agents SDK backend, seeded G1 English Ch.1) showed the dev backend never reached the model: it (1) read `getattr(message, "text")` but `claude-agent-sdk` puts assistant text in `message.content[].text` (so it collected nothing), and (2) passed `options={"system_prompt": ...}` as a raw dict where the SDK requires a `ClaudeAgentOptions` instance (raising `'dict' object has no attribute 'session_store'`). Both faults silently routed every dev call to the deterministic fallback — the "dev = Agents SDK" path (D-10) was effectively dead. *Apply:* iterate `message.content` blocks and append each block's string `.text`; construct `ClaudeAgentOptions(system_prompt=system)`. Verified live: the planner now returns valid LLM plans (e.g. merges "Greetings"+"My Name Is", splits "Letters A–E" into recognition/formation, places FAs) passing the validator with zero violations. Production (API-key) backend unaffected. *Decided:* 2026-06-03 (live verification).

**D-14 (follow-up, not yet implemented): the LLM occasionally returns non-strict JSON (prose/empty first chunk), so `plan_with_llm` intermittently fails to parse and falls back.** *Rationale:* During the same dry-run, one of two identical calls returned unparseable output; the fallback caught it safely but the intelligent plan was lost for that call. *Apply:* add a single "return JSON only, no prose" re-prompt retry inside `plan_with_llm` before raising `PlannerLLMError`. Tracked as bead `dars-icp-json-retry`; out of scope for the current PR. *Decided:* 2026-06-03.
