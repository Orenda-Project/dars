# Decision Log — Chapter Planner in Dars

**D-1: Planner units = lessons only; drop dars' auto-created assessment slots.** *Rationale:* The CPE planner emits exactly `period_count` lesson Plan Units and has no concept of FA/SA/revision slots. The current placeholder auto-appends a final formative `class_assessment_slot`; that behaviour is removed. Each Plan Unit becomes one `class_lesson_slot`. Teachers add assessments manually later (a separate flow, untouched here). *Apply:* Phase 2 — `generate_chapter_plan` writes only `class_lesson_slots`; the `class_assessment_slots` INSERT block is deleted. *Decided:* 2026-06-09 (user).

**D-2: Port the claude-agent-sdk backend into dars.** *Rationale:* User chose the agent-sdk (dev OAuth session) over reusing dars' `breakdown.llm_client` (Anthropic API key). `book_import_service` already uses `claude-agent-sdk` in the server, so the dependency and lazy-import pattern exist. The planner LLM backend mirrors the standalone `AgentSdkPlannerLLM` (D-13 content-block fix + `ClaudeAgentOptions` object). *Apply:* Phase 1 — `breakdown/planner_llm.py` ports `AgentSdkPlannerLLM`. *Decided:* 2026-06-09 (user). *Note:* dars' `llm_client.call_llm` (Anthropic API) stays for the rest of the breakdown engine; only the planner uses the SDK.

**D-3: Delete `chapter-planner-app/` after the dars integration lands.** *Rationale:* Single source of truth. Two planner implementations would drift. Once the planner core, agent-sdk backend, and `/plan` endpoint live in dars and the wire-up is green on staging, the standalone directory is removed in the same phase, along with the `make planner` target. *Apply:* Phase 2, final step. *Decided:* 2026-06-09 (user).

**D-4: Expose a dars `/plan` endpoint AND drive break-it-down internally.** *Rationale:* User wants both a directly-callable endpoint (mirrors the standalone `/plan`: PlanRequest in → ChapterPlan out, for testing/integration) and the internal use as the engine behind `generate_chapter_plan`. *Apply:* Phase 1 ships the endpoint; Phase 2 wires the internal call. *Decided:* 2026-06-09 (user).

**D-5: Carry the D-8 invariants and "no fallback" posture forward verbatim.** *Rationale:* The standalone planner validates output against five invariants and fails loudly (no repair, no retry, no deterministic fallback) — a bad plan raises rather than silently degrading. This is the right posture inside dars too: `generate_chapter_plan` surfaces the error to the caller. *Apply:* Phase 1 ports `validate_plan` + `make_chapter_plan` unchanged in behaviour. *Decided:* 2026-06-09. *Note:* Phase 2 must decide caller-facing error shape — a planner failure during break-it-down raises `ValueError`/dedicated exception that the router maps to a 4xx/5xx, consistent with existing `generate_chapter_plan` errors.

**D-6: `/plan` does not persist; break-it-down does.** *Rationale:* Matches the standalone split — `/plan` is a pure transform (no DB write, D-1 of the old app), while `generate_chapter_plan` is the persisting path. The endpoint and the internal driver share the planner core but differ in whether they write `class_lesson_slots`. *Apply:* Phase 1 endpoint is read-only; Phase 2 driver persists. *Decided:* 2026-06-09.

**D-7: Reuse dars' existing config for UG_LP and the staging DB; do not port the standalone `db.py` / `ug_lp_client.py` browse layer.** *Rationale:* The standalone app's `db.py` (read-only staging asyncpg) and `ug_lp_client.py` exist only because the app was process-isolated (old D-1). Inside dars the planner runs against the request's own DB connection and dars already has `generated_lps/lp_assistant_client.py` + `settings.lp_assistant_*`. The `/books`, `/books/{id}/chapters`, `/plan-input`, `/generate-lp-for-unit`, and the static playground from the standalone app are NOT ported — dars' dashboard already has book/chapter browse UI and a generation flow. *Apply:* Phase 1 ports only the planner core (models, prompts, parse, validate, agent-sdk backend) + a thin `/plan` endpoint. *Decided:* 2026-06-09.

**D-8: Build the PlanRequest for break-it-down from the live request connection, reusing the standalone `get_chapter_as_plan_input` query shape.** *Rationale:* The standalone `db.get_chapter_as_plan_input` already knows how to turn a `book_chapter_id` into a PlanRequest (topics ordered by `topic_number`; per-topic SLOs from `topic_sub_slos → sub_slos`, sub_slo UUID as the id, `[code] statement` as the statement). Phase 2's `generate_chapter_plan` builds the same shape from its `asyncpg.Connection` rather than a separate pool. *Apply:* Phase 2. *Decided:* 2026-06-09.

**D-9: A lesson slot tackles MULTIPLE topics — persist the unit's full topic grouping into `class_lesson_slot_topics`.** *Rationale:* User wants one lesson plan to be able to cover several topics (a Plan Unit already groups N `topic_ids`). The schema **already supports this**: `class_lesson_slot_topics` (migration `20260606000000`) maps one lesson slot to N ordered topics, built for exactly this (mirrors `class_assessment_slot_topics`; `generated_lps/service.py` already reads it). `class_lesson_slots.topic_id` stays as the **lead/primary** topic for back-compat — set to the unit's first topic_id. So Phase 2 persists each unit as one `class_lesson_slot` (lead topic on `.topic_id`) PLUS one `class_lesson_slot_topics` row per `topic_id` in the unit, `position` 1..N in `topic_ids` order. *Apply:* Phase 2, F2.2 — see 02-data-model.md. *No migration needed* (additive table already deployed). *Supersedes:* the "store only the first topic_id" choice flagged at plan review on 2026-06-09. *Decided:* 2026-06-09 (user).
