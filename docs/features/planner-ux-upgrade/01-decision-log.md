# Decision Log — Planner UX Upgrade

Frozen architectural decisions. To revise: ask the user, mark the old one
"Superseded by D-N+1 on YYYY-MM-DD", add the new one referencing the
supersession. Both stay. The decision log grows; it is never truncated.

This feature **inherits** the frozen decisions of
[`teacher-adjustable-syllabus`](../teacher-adjustable-syllabus/01-decision-log.md)
(D-1 advisory syllabus, D-6 reorder lock, D-7 teacher-set dates, D-10 auto-seed,
D-11 remove guard, D-13 Edit-syllabus toggle). None of those are superseded — the
"D-N" labels below are this feature's own and start fresh at D-1.

---

**D-1: The chosen UX pattern is anchor-date auto-pack + drag-to-reorder with downstream re-flow, with manual per-chapter override as an escape hatch.** *Rationale:* the user named two pain points — typing two dates per chapter, and reordering chapters one-by-one. The dominant pattern across mature timeline/Gantt tools (Asana Timeline, TeamGantt, Notion) and teacher planbooks (Planbook, Planboard) is: set a start, flow durations forward (skipping non-working days), and let a reorder re-flow everything downstream. This directly removes both pain points: the teacher types **one** date instead of 2N, and reorders by dragging instead of N×▲▼. We keep manual date entry available so a teacher can still pin an individual chapter. *Apply:* Phase 2. *Decided:* 2026-06-19 (user delegated the choice after a moderate research pass; chosen over "single date + computed duration" and "calendar range-picker" alternatives because it kills BOTH pain points, not just typing).

**D-2: No schema change, no new endpoint. Auto-pack and re-flow are pure client orchestration over the existing `setChapterDates` (PATCH) and `reorderChapters` (PUT) mutations.** *Rationale:* the class path already stores teacher-set `start_date`/`end_date`/`position` (D-7 of `teacher-adjustable-syllabus`); this feature only changes how those values are produced. The PATCH endpoint already COALESCEs a single bound and returns the full updated syllabus; the PUT endpoint already reorders with the D-6 lock enforced. Computing N consecutive ranges client-side and persisting them via N PATCH calls (or one reorder + N PATCHes) needs nothing new server-side. *Apply:* throughout. *Decided:* 2026-06-19. *Consequence:* a multi-chapter repack is several sequential PATCH round-trips; we batch them behind one `pathBusy` spinner and refetch once at the end (D-7).

**D-3: Holidays are SHOWN on the planner by reusing the existing `GET /api/v2/csts/{cst_id}/holidays` fetch — no new data, no teacher-side holiday editing here.** *Rationale:* the class page already fetches effective holidays for the Timetable tab (`holidaysApi.getCSTHolidays`, returning `effective_dates` + itemised `items`). The user asked for holidays to be *shown* on the teacher-app chapter planner. We lift that same fetch into the Syllabus tab's data path and render holidays inline; we do NOT add holiday CRUD to the planner (that lives on the Timetable tab / dashboard). *Apply:* Phase 1. *Decided:* 2026-06-19.

**D-4: Overlap (and holiday-in-range) warnings are CLIENT-SIDE and advisory — non-blocking, never reject a save.** *Rationale:* the user said "for the time being just client side warnings on when there is an overlap in the dates." The server already has the canonical algorithm (`compute_range_warnings` in `breakdown/chapter_calendar.py`: overlap when `cur.start <= prev.end` for position-consecutive dated chapters; plus gap and zero-teaching-days). We mirror that overlap + zero-teaching logic in TypeScript and add a holiday-in-range hint; we do NOT wire a server validation endpoint. The syllabus is advisory (D-1 of `teacher-adjustable-syllabus`), so warnings inform but never block. *Apply:* Phase 1. *Decided:* 2026-06-19. *Future:* a server-authoritative warning endpoint can replace the client mirror later without changing the UI contract; logged here so the mirror isn't mistaken for the long-term home.

**D-5: Manual override in v1 re-packs DOWNSTREAM only; it does not solve a constraint system.** *Rationale:* a full bidirectional constraint solver (pin chapter 5, ripple both ways, respect every lock) is out of scope for a UX upgrade. v1 behaviour: editing a chapter's start (or dragging it) re-flows every yet-to-start chapter *after* it, leaving earlier chapters untouched. This matches how planbook "bump" tools work (you bump from a point forward) and keeps the mental model simple. *Apply:* Phase 2. *Decided:* 2026-06-19. *Consequence:* if a manual edit creates an overlap with an *earlier* chapter, the D-4 overlap warning surfaces it rather than the tool auto-resolving it.

**D-6: Auto-pack respects the D-6 reorder lock — locked (in_progress/done) chapters are never repacked or reordered; packing starts after the last locked chapter.** *Rationale:* the past is immutable (D-6 of `teacher-adjustable-syllabus`). A chapter with taught history keeps its dates and position. Auto-pack and re-flow operate only on the contiguous tail of yet-to-start chapters; the anchor for that tail is the day after the last locked chapter's end date (or the teacher's chosen anchor if no chapter is locked). Drag-and-drop offers handles only on yet-to-start rows (the reorder endpoint enforces the lock server-side regardless). *Apply:* Phase 2. *Decided:* 2026-06-19. *Naming note:* this is THIS feature's D-6 and happens to enforce the ancestor feature's D-6; the overlap is coincidental.

**D-7: A multi-chapter repack issues its PATCHes sequentially behind a single busy state and refetches the syllabus once at the end — not optimistic per-row.** *Rationale:* each `setChapterDates` returns the full updated syllabus, but firing N in parallel races on `position`/`slot_count` recomputation and would thrash the UI. Sequential keeps server state coherent (each PATCH sees the prior one's result); one final state set avoids intermediate flicker. The existing `runPathMutation` wrapper already serialises a single mutation behind `pathBusy` — we extend it to await a list. *Apply:* Phase 2. *Decided:* 2026-06-19. *Consequence:* packing ~12 chapters is ~12 round-trips; acceptable for an explicit, infrequent "pack my term" action. If latency hurts, a future batch endpoint (D-2's deferred server work) collapses it to one call.

**D-8: Drag-and-drop uses `@dnd-kit` (sortable), not the HTML5 drag API or a heavyweight Gantt lib.** *Rationale:* `@dnd-kit` is the de-facto accessible, touch-friendly React sortable primitive — keyboard-operable, pointer + touch sensors (the planner is used on tablets), tree-shakeable, and styling-agnostic so it drops into the existing Tailwind/shadcn rows without a visual rewrite. The HTML5 drag API is fiddly on touch; a Gantt library is far too heavy for a single ordered list. *Apply:* Phase 2. *Decided:* 2026-06-19. *Acceptance:* if `@dnd-kit` is already a dependency, reuse it; otherwise add `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities`. Keyboard reorder (the existing ▲▼ semantics) must survive as the accessible fallback. *Build note (2026-06-19):* `@dnd-kit` was NOT a dependency — added `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` in Phase 2.

**D-9: (resolves O-1) An UNDATED chapter is sized during auto-pack by its org-breakdown teaching-day count when available, else a 5-period (one-teaching-week) default.** *Rationale:* an undated chapter has `slot_count == 0`, so the packer can't read its length from the class path. Most chapters are auto-seeded from the org's published breakdown (D-10 of `teacher-adjustable-syllabus`), which records the org's intended span — using it keeps the school's pacing. The org breakdown is reachable client-side: `SyllabusForCstResponse.syllabus_breakdown_id` → `breakdowns.getBreakdown(id)` → `SyllabusBreakdownDetail.chapters[]` (`SyllabusChapter`) carries `derived_teaching_days` keyed by `book_chapter_id`. Auto-pack fetches the breakdown once, builds a `book_chapter_id → derived_teaching_days` map, and for each undated chapter packs that many teaching days; a chapter with no org entry (or null `derived_teaching_days`) gets 5. *Apply:* F2.1 fetches the breakdown lazily on first auto-pack; the period count for packing chapter K = (dated → its `slot_count`) else (org `derived_teaching_days`) else 5. *Decided:* 2026-06-19 (user picked "Org breakdown span, else 1 week" over a flat default and over skip-undated). *Chosen over:* a flat 5-period default (ignores org-intended length) and skip-undated (fails the "one anchor packs everything" goal when chapters are undated).
